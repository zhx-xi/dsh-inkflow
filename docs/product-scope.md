# dsh-inkflow 产品范围（Product Scope）

> **一句话定位**：一个 DSH 插件（Host + Client 双半）在本地单机完成长篇小说的全部创作流程——SQLite 为真相源、复用 DSH 的 agent/skills/模型配置，不做 Chat UI、不做自研编排；差异化不在功能平铺（11 项基础能力竞品已全覆盖），而在「旧稿/设定 → 结构化资料库的提取管线」「系列共享设定 / 同世界观多故事」「结构化深度（多纪元历法 + 双时间轴 + 知识图谱 + 地图）」三点。

## 1. 定位与产品形态

### 1.1 产品定义

| 维度 | 内容 | 来源 |
| --- | --- | --- |
| 是什么 | 一个 DeepSeek Harness（DSH）插件，目标「一个插件完成长篇小说创作全部功能」 | 【已定】 |
| 为什么是单插件 | 不拆多插件，避免插件冲突与升级兼容问题 | 【已定】 |
| 交付形态 | DSH 插件包（Host 半 + Client 半），不是独立桌面应用、不是 Web 服务 | 【已定】 |
| 技术栈 | 纯 TypeScript | 【已定】 |
| 运行边界 | 第一阶段完全本地单用户；不做账号 / 计费 / 远程服务端，仅在架构上预留同步 / 存储 / 认证接口 | 【已定】 |
| 数据位置 | 数据目录 `$DSH_HOME/inkflow/`（本机 `DSH_HOME` 默认为 `~/.dsh`，库文件 `inkflow.db`）+ 用户可选作品库目录 | 【已定】 |
| 持久化 | `node:sqlite`（DSH 宿主 Node 24 内置），SQLite 为唯一真相源 | 【已定】 |
| 许可 / 可见性 | 仓库 public、MIT | 【已定】 |
| 迁移节奏 | 旧库数据迁移不在第一阶段，安排在后续阶段（见 roadmap P4） | 【已定】 |

### 1.2 DSH 插件双半形态

| 半 | 运行位置 | 职责 | 来源 |
| --- | --- | --- | --- |
| Host 半 | Node 进程内 | 工具注册、HTTP 路由、systemPrompt 注入、后台任务 | 【已定】 |
| Client 半 | React | 注册左栏图标 + main 整页面板 | 【已定】 |

### 1.3 复用与自制边界（这是本项目最大的架构约束）

| 事项 | 复用 DSH | 自研 | 来源 |

| 工具注册 | — | 是：约 20–30 个 `inkflow_*` 工具 | 【已定】 |
| HTTP 路由 | — | 是（Host 半内，`/inkflow/api/*` 前缀；仅 loopback、fail-closed，ADR-0004） | 【已定】 |
| systemPrompt 注入 | — | 是（注入写作上下文/简报） | 【已定】 |
| 后台任务 | — | 是（提取管线、批量写作、久任务） | 【已定】 |

| 页面宿主 | — | 是（React 面板，**禁止 iframe**） | 【已定】 |

### 1.4 硬性技术禁忌（来自定位，不是建议）

## 2. 目标用户

> 本节规格未给出，全部为【推断】。四类画像用于校验功能全集的完整性，不影响功能取舍。

| 用户类型 | 规模假设 | 典型场景 | 核心诉求 | 对应功能（§4） | 来源 |
| --- | --- | --- | --- | --- | --- |
| 长篇小说作者（连载/完本） | 1 人 1 库，3–10 本并行 | 每天写 1–3 章、维护庞大设定 | 设定不崩、伏笔不漏、章节可批量产出 | P0 全部 + P1 账本/门禁/简报 | 【推断】 |

| 系列 / 同世界观多故事作者 | 1 人，2–5 本共享世界观 | 一部作品衍生多部，设定同步 | 设定只维护一份、不各改各的 | P2 系列共享设定 + 同世界观完全同步 | 【推断】 |
