## 2. spec 编写规范

**写「是什么」，不写「怎么做」。**

- ✅ 数据形状、字段语义、契约与边界、错误码、验收判据、不变量
- ❌ 实现代码、函数体、迁移 SQL、具体文件路径的逐行实现
- ✅ 计划中的契约必须显式标【未实现】并给出归属（issue / 模块），不得写成现状
- 数字优先：能给阈值就给阈值（行数、耗时、数量），不给「较快/较多」
- 待裁决项集中在 [S-06](open-questions.md) §1；拍板后转入 §2「裁决记录」（原推断 / 处置 / 原话依据）

## 3. 变更流程

1. **改 spec 先行**：任何行为变化，先在对应 spec 落定契约；
2. 若涉及技术选型/架构边界/数据格式/对外契约 → 先写 [ADR](../adrs/)；
3. 再写测试（RED）→ 实现（GREEN）；
4. 提交时 `pnpm.cmd run check` 全绿，并跑一次链接检查。

**spec 与实现矛盾时，以 spec 为准并修实现；若发现 spec 本身错，先改 spec 并说明理由。**
