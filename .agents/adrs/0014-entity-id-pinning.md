# ADR-0014：实体改名用「id 钉住」，不级联重写引用

- 状态：已采纳（2026-10-24）
- 日期：2026-10-24

## 背景

除章以外的实体，`id` 缺省等于项目内相对路径：

```ts
// src/host/domains/world.ts:50（characters / outlines / timeline / relations 同形）
id: stringField(parsed.data, 'id') ?? path,
```

于是**改名＝换 id**。而引用这些 id 的地方至少有五处：

| 引用方 | 字段 | 来源 |
|---|---|---|
| 关系 | `source` / `target` | `relations/<slug>.md`，I-08 要求两端都存在 |
| 时间线 | `participants` / `place` | `timeline/<slug>.md` |
| 账本 | `subject` | `facts/<subject>.md` |
| 伏笔 | `linkedEntities` | `foreshadowing/<slug>.md` |
| 实体提及 | `entity_mentions.entity_key`（`kind:id`） | 派生索引 |

#34 的验收要求「改名后引用不断链、取消操作时零写入」。两条路线在这一点上分叉：

- **级联重写**：改名时把所有引用方文件一起改，把旧 id 换成新 id。要写 N 个文件（N = 引用条数），跨文件无事务，中途失败就会留下半改状态；而且要遍历全书找引用（耗时随书增长）。
- **id 钉住**：改名只写一个文件——把**旧 id** 写进新文件的 `id` 字段。id 从此与路径解耦，引用方**一个都不用动**。

[data-model](../specs/data-model.md) §3.1 已经明确「其余实体：缺省用相对路径（改名即换 id，**建议显式写**）」，即显式 `id` 本来就是合法且被推荐的写法。id 钉住不需要新机制，只需要在改名时执行这条既有建议。

## 决策

1. **改名 = 移动文件 + 钉住旧 id**：把旧 `id` 写进目标文件 frontmatter 的 `id`（若原本没有 `id` 字段则新增一行；若有且与旧 id 相同则不动）。引用方（上表五处）**不重写**。
2. **影响清单是「告知」不是「重写清单」**：#34 在改名/改设定前列出受影响的章与实体（基于 `entity_mentions` + 关系 + 引用字段），用户确认后**只执行那一次写**。清单里的条目不需要逐个改。
3. **id 与路径分叉是合法状态，不是错误**：新增不变量 I-20 `ID_PATH_DIVERGED`（**info 级、不阻断**），由体检（#33）列出「id 与路径不一致」的条目，供作者知道「这个名字换过、旧引用还靠这个 id 活着」。
4. **新建实体不钉 id**：新建时 `id` 仍缺省等于路径（少一行噪声）；只有「改名」这一个动作会写 `id`。判据是**文件真的换了名字**（目标路径 ≠ 当前路径）：只改显示名的编辑不写 `id`——否则文件会声称自己改过名，I-20 也跟着误报。
5. **重复改名保持同一 id**：第二次改名沿用文件里已有的 `id`，不再生成新的。

## 备选与取舍

| 方案 | 优点 | 代价 | 为什么没选 |
|---|---|---|---|
| 级联重写引用 | id 始终等于路径，心智简单；索引不必有 `ID_PATH_DIVERGED` | N 个文件同一动作，无事务；中途失败留半改状态（违反「取消时零写入」）；遍历全书找引用随规模变慢；git diff 巨大且不可逐条审阅 | 把一次写变成 N 次写，正好踩在 data-safety「危险操作要小、可回滚」的反面 |
| 强制所有实体必须有显式 id（迁移存量） | 一次把事情做干净 | 要一个全库迁移器，且存量文件的 diff 全是机械改动；#36 的迁移范围会被这条挤压 | 收益只是「id 好看」，代价是一次全量重写 |
| 用「路径即 id」并在改名时禁止有引用的实体改名 | 零机制 | 作者最想改名的正是被引用最多的核心条目（主角、宗门、境界） | 把功能砍在最有用的地方 |
| **旧 id 钉住**（选中） | 一次写、单文件、可 CAS、可回滚；引用永不悬空 | id 与路径分叉后，读 id 猜不到文件在哪（要靠索引/`path` 列） | — |

## 后果

| 收益 | 代价与对策 |
|---|---|
| 改名是一个文件的一次写，天然满足「取消时零写入」 | id 与路径分叉 → 所有「按 id 找文件」的地方必须走索引的 `path` 列，不能拼路径。用例：改名后 `entities` 行的 `id` 不变、`path` 更新 |
| 引用永不悬空，`DANGLING_PARENT` / `RELATION_ENDPOINT` 不会因改名爆发 | 不能靠「路径 = id」做去重判断 → 唯一性仍按 `(kind, id)`，重复 id 报 `DUPLICATE_ID` |
| 与章（uuid，改名不变）的语义一致 | 两类实体的 id 生成规则不同（章 uuid / 其余路径或钉住），spec 里要写清（[data-model](../specs/data-model.md) §3.1 已分列） |
| 体检能列出「名字换过」的条目 | 只有**原本没有显式 id、改名后 id 变成路径形状**的条目会被列出（`id ≠ path` 且 id 含 `/`、以 `.md` 结尾，章除外）。**手写短 id 的书不会收到这条提示**——真实书里 21/21 条世界观条目都写 `id: w-1` 这类短 id，它们从来没等于过路径，报「这个名字换过」是假话；多一个 info 级 code，不影响阻断判定 |

## 验证

- `tests/identity.test.js`（#34）：改名后关系端点仍解析、`entities` 行 id 不变且 path 已更新、`entity_mentions` 命中条数不变；改名前后 `git status` 只多一个文件、少一个文件。反证两条：只改显示名时文件里**没有**新增 `id:` 行；改名后再删掉该文件，`RELATION_ENDPOINT` 才出现（钉住的是 id，持有 id 的是文件）。
- `tests/invariants.test.js`：`ID_PATH_DIVERGED` 只报 info，不阻断写入；`DUPLICATE_ID` 仍按 `(kind, id)` 判。
- 取消路径：改名计划生成后不执行 → 项目根全量 hash 不变（沿用 `hashTruth` 手法）。
