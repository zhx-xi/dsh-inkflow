# ADR-0009：语义检索复用 OpenViking（peer 从工作区读、按章重建、召回不等于定位）

- 状态：**已采纳（2026-10-21）**
- 日期：2026-10-21
- 关系：扩展 [ADR-0005](0005-files-first-with-derived-index.md)（FTS5 派生索引照旧，语义检索是**叠加层**）；遵守 [ADR-0006](0006-workspace-contract-v2.md) D5（一个工作区一部书）与 [ADR-0007](0007-plugin-shared-library.md) C1/C7（共享库位置与私有配置不入库）
- 影响：`src/host/indexer.ts`（索引表与降级路径）、[S-02 architecture](../specs/architecture.md)（检索数据流）、[S-04 data-model](../specs/data-model.md)（语义检索的派生表与定位字段）、[docs/user-guide.md](../../docs/user-guide.md)（费用与体积提示）

## 背景

1. 长篇需要两种检索：**关键词**（人名、地名、术语，精确）与**语义**（"那把断剑" ↔ "残锋"，跨章召回）。关键词已由派生索引的 FTS5 承担（[S-03](../specs/conventions.md) §4）。
2. 项目硬约束是**零运行时依赖**、纯 TS、`node:sqlite` 只做派生索引。自研 embedding 意味着自带模型权重或原生扩展——与"零依赖"直接冲突。
3. OpenViking（下称 OVK）已在同一台机器、同一宿主进程内可用：memory 插件通过 `ctx.provide("openvikingMemory", runtime)` 提供运行时，其 HTTP 面包含检索端点（`/api/v1/search/find`、`/api/v1/search/search`、`/api/v1/search/recall`）；embedding 是**本地** `bge-m3`（`~/.openviking/ov.conf` 的 `embedding.dense.api_base = http://127.0.0.1:11435/v1`，1024 维），语义摘要走 `deepseek-flash`（**会产生真钱费用**）。
4. OVK 的工作区配置层：`<会话工作区根>/.openviking/config.json`（团队，可提交）与 `config.local.json`（私有，覆盖前者），schema 为 `{"version":1,"peer":{"id":"…"}}`；workspace 键 `peer.id` / `peer.source` 等少数几个生效。约束（OVK 客户端实现）：`version` 必须为 `1`（否则**整层被忽略**）、文件 ≤ 64 KiB、经 symlink 逃出工作区会被拒绝、`${VAR}` 不展开、连接与凭据类键被剥离、`peer.id` 需过服务器 `sanitizePeerId`（仅 `[A-Za-z0-9_.@-]`，连续 `-` 合并，≤100 字符，`ext-`→`x-`，`__self`→`self`，**中文会被删成空**）。已解析 peer 对会话是固定的，改配置后需新会话才生效。
5. W0 探针结论（issue #12 收尾评论，见本文「验证」证据附录）：peer 生效优先级、跨 peer 读需 `recallPeerScope=all`、**`forget` 是永久物理删除**、检索结果只能定位到**文件**（uri + abstract）不能到章/段、共享库 peer 尚不存在（可自动建父链）、MCP 数据面的 actor peer 是**进程级**（boot cwd）而非会话级。

## 决策

### P1 不自研检索：语义能力由 OVK 提供

InkFlow **不**引入 embedding 模型、向量库或原生扩展，不新增运行时依赖（`dependencies` 保持为空）。语义检索的向量化、召回排序、跨语言相似度都由 OVK 负责；InkFlow 负责**哪本书的哪些内容**、**怎么写进去**、**召回后怎么定位回原文**。

### P2 peer 只从工作区配置读

| 项 | 决定 |
|---|---|
| 来源 | `<工作区根>/.openviking/config.local.json`（私有，优先）→ 缺则 `.openviking/config.json`（团队层） |
| 读取范围 | **只读 `peer.id`**；不读 `peer.source`、不读任何其他键作为业务输入 |
| `peer.source` | 工作区只设 `peer.source`（模板派生）而没有 `peer.id` 时：语义检索降级，并提示"请显式写 `peer.id`"。InkFlow **不**自己实现模板派生——那是 OVK 的解析规则，重写一份必然漂移 |
| 写回 | **不写**这两个文件；不改写、不重排、不格式化、不删除未知键（保留它们，避免破坏 OVK 自己的配置） |
| 校验 | 保持 OVK 的约束：`version` 必须为 `1`（否则按"无 peer"处理，不自行"修复"）、文件 ≤ 64 KiB；`peer.id` 只允许 ASCII 字符集，含非 ASCII 时**拒绝使用并提示改写**（服务器会静默删成空串，比报错更糟） |
| 缺失 | 都没有 `peer.id` → 该工作区**不做**语义检索（只 FTS5）。**不静默编一个 peer**（例如用目录名/仓库名推导），否则同一本书在不同机器上会分裂成不同命名空间 |
| 生效时机 | peer 对会话是固定的：改了工作区配置需**新开会话**才生效；面板与工具都按当前解析结果回显，避免"看起来改了但其实没生效" |

### P3 每次请求显式携带 peer

写入与召回**都显式**携带 actor peer（请求头 / URI 全限定），**不依赖**进程 boot cwd 的隐式 peer（探针 E3：MCP 数据面的 actor peer 是进程级）。跨 peer 读（项目读共享库）需要 `recallPeerScope=all`；该开关不可用时降级为"共享库只参与复制、不参与召回"，并提示原因。

### P4 共享库 peer：`dsh-inkflow-common-shared`

- 共享库（[ADR-0007](0007-plugin-shared-library.md) C1）的语义内容固定写入 peer `dsh-inkflow-common-shared`，与各书的项目 peer 分离。
- 首次使用时**自动创建**（OVK 会自动补父链）；若创建或写入被权限策略拒绝 → 共享库语义检索不可用，**复制 / 引用功能不受影响**，只丢"跨书语义召回"这一项增强。
- 该 peer **不是**用户手填项：不接受工作区配置覆盖（否则不同机器各写一个共享 peer，跨书召回失效）。

### P5 写入单位：一章一重建单元

- 重建以**章**为单位：章文件变化 → 只重写该章的块，不动其他章。
- 章内按段落聚合成块，块带上限与重叠（具体数值由 spec 定）；每块必须带定位元数据：`chapterId`、`seq`、`blockIndex`、`contentHash`、`deleted`。
- 写入走**同路径覆盖**：同一块的 URI 固定（由 `projectId` + `chapterId` + `blockIndex` 决定），内容变了就覆盖同一路径，不追加新路径。因此重复重建是幂等的，不会产生重复条目。

### P6 删章不调用 `forget`；软删必须自建

探针 E4：`forget` 是**永久物理删除**（先删向量再删文件，无回收站）。因此：

1. **写作流程与删章动作永不调用 `forget`**（也不把 `forget` 暴露给写作 Agent）。
2. 删章 = 三步：① 文件层进项目自建回收站（软删，ADR-0006 的九个目录之外，由索引记录 `deleted` 状态）；② OVK 侧把该章的每块**覆盖为 tombstone**（正文清空 + `deleted: true` + 新 `contentHash`）；③ 自有索引把该章标 `deleted`，召回结果里**过滤掉** `deleted` 的块。
3. **物理 `forget` 只在用户显式动作**「清理已删除章节的语义条目」里执行：先列出待删 URI 清单（数量 + 逐条路径）并要求确认，逐条删除，失败即停并报告。
4. **整库重建不做"先 forget 再重建"**：重建 = 逐块同路径覆盖 + 孤儿清零（只对确认过属于本项目、且已不在索引里的 URI 执行清理，且同样要求确认）。

### P7 召回只做"找到"，定位由自有索引完成

- OVK 返回的是**文件级**结果（uri + abstract）。`abstract` 是摘要，**不是正文、不是段落**——不得进写作上下文、不得当引用原文展示。
- 定位链：`uri` → 自有索引的块记录 → `{chapterId, seq, charRange}` → **回文件读正文**。
- 若 uri 在自有索引里找不到（索引落后 / 被外部改过），标 `staleIndex` 并触发该章重建，而不是猜一个章节号。

### P8 降级：无 OVK 时仍是可用的关键词检索

| 条件 | 行为 |
|---|---|
| OVK 不可达 / 健康检查失败 | 只用 FTS5（trigram ≥3 字 + 2 字 `LIKE` 兜底，ADR-0005 后果表） |
| 工作区没有 `peer.id` | 同上（语义检索不可用，关键词可用） |
| 索引尚未建成 / 某章块缺失 | 关键词结果照常返回；语义结果标 `partial` |
| 降级发生 | 响应带 `searchMode: "fts5"` 与 `degradedReason`；不阻塞任何非检索功能，不写盘 |

降级是**能力降级**，不是错误：检索接口不因 OVK 缺席而失败。

### P9 首建范围

| 纳入 | 不纳入 |
|---|---|
| 正文（`chapters/**`）、设定/世界观（`world/`）、角色（`characters/`）、关系（`relations/`）、账本（`facts/`） | `library/` 的**原文**（体积不可控、多为第三方文本、许可未定、解析成本高） |

- `library/` 只有**索引卡**（`library/*.md`，ADR-0007 C1）进入检索，卡片里的原文副本不进入。
- 共享库侧同样只索引共享条目本体（`world/`、`snippets/`、`library/` 卡片），不索引原文副本。
- 纳入范围之外的域，检索不返回、也不留空壳条目。

### P10 费用与体积提示（首建前必须给出）

- embedding 是**本地**模型（无 API 费用，占 CPU/显存与磁盘）；**语义摘要会产生真实的 LLM 费用**（`deepseek-flash`），一次语义摘要的调用次数与"资源文件数"同阶——按章重建时约等于章数。
- 首建前给估算并要求确认，至少包括：章数、预计块数、预计新增体积、预计摘要调用次数；超过阈值（具体阈值由 spec 定，例如 >200 章或 >5 MB）必须显式确认，否则只建关键词索引。
- 量级参考【推断，非实测】（探针 P5 明确标为【未验证】：本机当时禁止写入实测）：10 章 × 3 000 字 = 3 万字，按 800 字/块、100 字重叠计（有效步长 700 字）约 40–45 块；每块文本约 2.4 KB（中文按 UTF-8 3 B/字）+ 向量 1024 维 × 4 B ≈ 4 KiB，合计约 0.3–0.4 MB / 3 万字 → 10 万字（约 145 块）约 1–2 MB 量级（不含 OVK 自身的索引与摘要开销）。
- **未定项（转入 spec + 探针）**：块大小与重叠的具体数值、URI 模板（项目子树与共享库子树）、`write` 的落点究竟是 resources 还是 peer memories（探针 E6 的【未验证】项），以及 OVK 只读策略是否拦 `write`——两项落点都不得改动 OVK 的只读策略。

## 备选与取舍

| 方案 | 优点 | 代价 | 为什么没选 |
|---|---|---|---|
| **自研 embedding + 向量表**（`sqlite-vec` / 手写余弦相似度） | 零外部服务，完全自控 | 需要模型权重或原生扩展，与"零运行时依赖"硬冲突；还要自己实现分块、召回、重排 | 等于自研一个检索引擎；`node:sqlite` 无向量索引，纯 JS 全表扫描在长篇规模上不可用 |
| **只用 FTS5 关键词**（不接语义） | 简单、零成本、无外部依赖 | 跨章语义召回做不到（同义、代称、意象），而这正是长篇最需要的能力 | 保留为**降级路径**（P8），不作为唯一能力 |
| **把删章映射到 `forget`** | 一行搞定，索引立刻干净 | `forget` 是永久物理删除（先删向量再删文件、无回收站）；写作 Agent 一次误删不可恢复 | 数据安全红线；改为 tombstone + 用户显式清理（P6） |
| **每章一个独立 peer**（`book-<id>-ch-<n>`） | 删章 = 删 peer，隔离彻底 | peer 数量爆炸（一本 500 章 = 500 peer）；跨章召回要跨 peer；peer 对会话是固定的 | 命名空间粒度选错：peer 应表达"这是哪本书/哪个共享库"，章用块路径表达 |
| **自建向量库 / 独立检索进程** | 完全可控，可自定义排序 | 引入第二个常驻服务与一套运维（端口、健康、升级、崩溃恢复） | 已经有一个本地可用的 OVK；重复建设且违背"一个插件完成全部功能"的边界 |
| **把 `abstract` 当正文写进上下文** | 省一次文件读，快 | `abstract` 是 OVK 生成的摘要，不是原文；会污染引用与写作上下文，且无法定位到段 | 定位必须回文件（P7）；摘要只能当"提示这是哪一段"的线索 |
| **首建就把 `library/` 原文纳入索引** | 检索面更全 | 体积与费用不可控（PDF/图片/扫描件）、第三方文本许可未定、解析成本高 | 先做可控范围（P9），原文按需再评估 |
| **让用户手填 peer（自定义配置项）** | 显式、可控 | 与 OVK 的工作区配置重复，两处真相；改一处忘一处就分裂命名空间 | 复用 OVK 已有层级（P2），InkFlow 只读不写 |

## 后果

### 正面

- 长篇的两种检索都可用：精确（FTS5）+ 语义（OVK），且语义缺席时功能不塌。
- 零运行时依赖不变；embedding 本地跑，不外发正文到第三方 embedding API（语义摘要除外，且可提示）。
- peer 语义与 OVK 自己的记忆一致：同一工作区、同一命名空间，换机器靠工作区配置收敛。
- 删章可恢复：tombstone + 回收站 + 显式清理，`forget` 不再是隐藏的永久删除。

### 负面

- 多一个外部依赖（OVK 服务与本机 embedding 服务）：它们不在时只剩关键词检索。
- 成本不可见的部分在"语义摘要"：按章重建会按章计费，用户容易低估（P10 用估算 + 确认兜住）。
- tombstone 会长期占用体积，直到用户执行清理。
- 索引两套（自有 SQLite + OVK 向量）→ 一致性靠"同路径覆盖 + hash"维持，需要 stale 检测与重建动作。

### 风险

| 风险 | 触发条件 | 对策 |
|---|---|---|
| 费用失控 | 首建/重建反复触发 | 首建估算 + 阈值确认（P10）；重建只对变更章执行（P5）；不做自动全量重建 |
| peer 配错导致跨书污染 | 把 A 书的 `peer.id` 复制到 B 书工作区 | `peer.id` 只读且不代填（P2）；汇总接口回显当前 peer；文档提示 `.openviking/config.local.json` 不入库（ADR-0007 C7） |
| `forget` 被误用 | 后续实现"清理"时顺手调用 | `forget` 只出现在显式清理动作里，且必须先列清单确认（P6）；写作工具不暴露 |
| OVK 升级改语义 / 改端点 | 宿主或 OVK 升级 | 检索是**可降级增强**：端点/字段变化只会让语义检索掉到 FTS5，不影响数据与写作 |
| 共享库 peer 被权限策略拒绝 | OVK 只读或命名空间受限 | 共享库语义检索标"不可用"，复制/引用照常（P4） |
| 索引落后导致定位失败 | 文件被外部改过、重建被中断 | 返回 `staleIndex` 并触发该章重建，不猜章号（P7） |

### 判据（**验收判据，不是现状陈述**；用例落在 `tests/`，实测证据贴对应 PR 评论、不入库）

| # | 场景 | 期望（判据） |
|---|---|---|
| V1 | 工作区只有 `.openviking/config.local.json` 设了 `peer.id` | 使用的 peer 为它；profile 默认值不生效；文件内容 hash 前后一致 |
| V2 | `config.local.json` 的 `version: 2` | 该层被忽略（按"无 peer"降级到 FTS5）；不"修复"文件、不写盘 |
| V3 | `peer.id` 含中文 | 拒绝使用并提示改写为 ASCII；不写入 OVK、不编造 peer |
| V4 | 改一章正文后重建 | 只有该章的块被覆盖；其他章块 URI 与内容 hash 不变；重复重建幂等（块总数不变） |
| V5 | 删一章 | 文件进回收站；该章块变 tombstone；召回不再返回；**OVK 侧无物理删除**（`forget` 调用次数 = 0） |
| V6 | 执行「清理已删除章节的语义条目」但取消确认 | 零删除；再次执行并确认后只删清单内 URI，逐条报告 |
