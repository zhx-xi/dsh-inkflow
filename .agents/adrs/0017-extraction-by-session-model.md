# ADR-0017：提取由「会话里的模型」产出，插件只做队列与落地

- 状态：已采纳（2026-10-24）
- 修订：[ADR-0021](0021-candidate-duplicate-and-overwrite.md)（2026-10-25）改了 D4 的一个结论——「采纳从不覆盖」不再是绝对的：同身份同内容在提交时就跳过，同身份异内容在作者显式 `overwrite` 下会替换（先落 `replace` 备份包）。本文其余部分（模型只产出候选、插件只做队列与落地、`.inkflow/candidates/`）不变。
- 日期：2026-10-24

## 背景

0.4.0 的 #38 要把旧稿与设定变成结构化资料库，核心是「6 类实体提取」。这里有一个绕不开的问题：**谁来跑模型？**

三条已定的约束把答案挤到只剩一个：

1. **零运行时依赖**（[AGENTS.md](../../AGENTS.md) §2）：插件不能带 LLM SDK、不能带 embedding 库。
2. **不做对外 API、不引入第二个消费者**（[ADR-0008](0008-panel-data-channel.md) 背景 8）：插件没有自己的 HTTP 客户端身份，也不该持密钥。
3. **绝不静默入库**（product-scope F-P1-08 / A-19）：候选必须经作者确认才能变成实体文件。

而 DSH 里**本来就有**一个会读会写的模型：作者开会话时那个。它已经能读正文（通过工具）、已经理解中文小说结构、也已经在用 `inkflow_*` 工具。让它产出候选，插件只负责「收、存、审、落」，是唯一不需要新依赖、不新增密钥、又能保住「不静默入库」的形态。

## 决策

### D1 插件不调用任何 LLM

`src/host/` 里没有、也不会出现「调模型」的代码。提取的智能来自会话里的模型；插件提供的是**结构**（候选形状、存储、审阅、落地）与**门禁**（不确认不入库）。

### D2 候选由工具提交，形状固定

模型通过 `inkflow_extract_propose` 提交候选，每条至少包含：

| 字段 | 语义 |
|---|---|
| `kind` | 6 类之一：`character` / `world` / `outline` / `timeline` / `foreshadowing` / `relation` |
| `fields` | 该类的字段（与 `data-model.md` §3 的字段字典同名，不为提取另造一套） |
| `evidence` | **必填**：`path#L<n>`（正文行锚）或章 id；没有证据的候选直接拒 |
| `rationale` | 一句话：为什么从这段文字推出这条 |
| `confidence` | `high` / `medium` / `low`（只用于排序与展示，不参与任何自动决策） |
| `candidateId` | 由插件发放（`ex-<8 位十六进制>`），模型不自造 |

一次提交是一**批**（`proposals[]`），插件为每条分配 id 并落盘（D3）。

### D3 候选落 `.inkflow/candidates/`，不落 `index/`

`index/` 是派生物且缺失即重建（[ADR-0006](0006-workspace-contract-v2.md) D2），而候选是**待作者审阅的工作物**：重建一次索引不该让一小时的提取结果消失。落点因此与回收站/备份同一条纪律（[ADR-0012](0012-plugin-private-state-dir.md)），白名单从三条子路径扩到第四条 `candidates/`。

文件形状：`.inkflow/candidates/<时间戳>-<kind>.json`，一份提交一个文件（`{ schemaVersion, submittedAt, source: {chapters[]}, proposals[] }`）；已处理的候选**保留**（可追溯），由显式 `purge` 清理。

### D4 采纳才写真相，且走与手写完全相同的路径

`inkflow_extract_accept`（要 `confirm: true`）逐条采纳：读候选 → 交给对应域模块的 `parseFile` / `validate` → 走 `io.ts` 写入 + 写锁 → 重建索引。**没有第二条写入路径**：候选 JSON 永远不会被「转换成文件」的旁路代码直接搬进内容目录。

拒绝（`inkflow_extract_reject`）只改候选状态，**不产生任何文件**，也不删已存在的同名实体（拒绝一份候选不等于回滚一次采纳）。

### D5 「静默入库 = 0」是结构保证，不是测试保证

唯一的入库入口是 `accept`，而 `accept` 要求 `confirm: true` 且逐条给 `candidateId`。测试仍会钉住它（`入库集合 ⊆ 已确认集合`），但即使测试被删，代码里也没有别的路。

## 备选与取舍

| 方案 | 优点 | 代价 | 为什么没选 |
|---|---|---|---|
| 插件内置 LLM 客户端（HTTP 直连某家 API） | 一键提取，用户不用开会话 | 引入依赖与密钥管理；违反零依赖；密钥落磁盘是新的安全面 | 与 ADR-0008「不做第二个消费者」直接冲突 |
| 外部 CLI 提取（子进程调 `inkflow-mcp` 之类） | 复用现成工具链 | 引入进程管理与平台差异；第二次安装；错误面变成「子进程挂了怎么办」 | 插件形态是嵌入 DSH 的单机工作台，不该自带 sidecar |
| 模型直接写实体文件（不经候选） | 最少代码 | 无法审阅、无法批量回退、静默入库风险全靠模型自觉 | 违反 F-P1-08 的「绝不静默入库」 |
| **模型产出候选 + 插件队列与落地**（选中） | 零依赖、零密钥；候选可审阅可回退；入库路径唯一 | 提取质量取决于会话里的模型；需要一套审阅 UI | — |

## 后果

| 收益 | 代价与对策 |
|---|---|
| 插件保持零依赖、无密钥 | 作者必须在一个会话里发起提取（不能「后台自动跑」）；对策：候选落盘后可跨会话审阅，同一个候选批次不必在同一会话里完成 |
| 候选可审阅、可回退、可追溯 | `.inkflow/candidates/` 会长大；对策：`purge` + 面板显示总量，不做自动清理（与 ADR-0012 #4 一致） |
| 入库只有一条路 | 采纳一条候选要过一次 `validate`，可能与既有实体冲突（重名、重复 id）——这是**对的**，冲突该在采纳时暴露，而不是入库后发现 |
| 与 #39 的检索、#41 的语义检索解耦 | 提取不使用向量检索（模型自己读正文），三者可分别交付 |

## 验证

- `tests/extract.test.js`：没有 `evidence` 的候选被拒；`accept` 前内容目录零新增文件（全树 hash）；`accept` 后实体文件与手写同形（同一 `parseFile` 读回）；`reject` 零写入；同一 `candidateId` 重复提交是更新而非新建。
- 结构断言：`src/host/extract.ts` 之外没有任何模块引用候选 JSON（`grep` 式守卫），保证「只有一条入库路径」。
- 端到端：10 章正文 → 模型提交 ≥4 类候选 → 采纳 2 条、拒绝其余 → `inkflow_project_audit` 无新增告警、被拒候选零文件。
