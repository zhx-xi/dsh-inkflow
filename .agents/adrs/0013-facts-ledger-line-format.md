# ADR-0013：事实账本 `facts/<subject>.md` 的行内编码（正文列表项 + 竖线分隔键值）

- 状态：已采纳（2026-10-24）
- 日期：2026-10-24

## 背景

账本（#32）的真相文件是 `facts/<subject>.md`：**一主体一文件、一文件多条事实**（[data-model](../specs/data-model.md) §3.5）。跨章校验的输入是同一 `subject + attribute` 的多个 `since` 区段，所以一个文件里必须能排下任意多条、可增删、diff 友好的记录。

三个实测约束决定了格式：

1. **frontmatter 不能承载这些记录**。项目读取器只支持标量、行内数组与块数组；**嵌套映射会被读回成一整个字符串**（[data-model](../specs/data-model.md) §3.4 记录过同一现象，时间线 `worldTime` 因此定为扁平标量）。一条事实有 6 个字段，表达成「映射数组」正好落在不支持的形状上。
2. **不能一条事实一个文件**。§3.5 已把文件粒度定在 `subject`，且跨章校验要按 `subject + attribute` 聚合——拆成 N 个文件会让每次校验都要读 N 个文件。
3. **行锚要能定位**。findings 的 `locator` 要跳到具体一条事实（X-14），所以每条记录必须落在正文的**可数行**上。

## 决策

事实写在正文，一条一个列表项，字段用竖线分隔：

```markdown
---
subject: char-qingyin
---

- attribute: 境界 | value: 筑基后期 | since: ch-0007 | chapterId: ch-0009 | source: text
- attribute: 境界 | value: 金丹初期 | since: ch-0042 | chapterId: ch-0045 | source: text
- attribute: 持有物 | value: 青锋剑 | since: ch-0012 | until: ch-0061 | chapterId: ch-0012 | source: manual
```

规则（写入与读取必须同源实现，见「验证」）：

1. **行的形状**：`- ` 开头（允许行首缩进 ≤3 空格），随后是 `键: 值` 段，段间用 `|` 分隔，首尾空白忽略。
2. **键集合**：`attribute` / `value` / `since` / `until` / `chapterId` / `source`；`attribute` 与 `value` 必填，其余可缺省。缺省 `until` 表示**至今仍成立**；缺省 `source` 视为 `manual`。
3. **`|` 冲突**：`value` / `attribute` 里要含字面 `|` 时写成 `\|`；读取时反转义。写入侧一律转义，读取侧容忍未转义但**不猜测**（未转义的 `|` 就是分隔符）。
4. **未知键保留**：与 frontmatter「未知字段保留、索引忽略」同一策略——不报错、不丢、写回时原样保留。
5. **不可解析的行**报 `FACT_LINE_MALFORMED`（warning，行锚 `path#L<n>`），不阻断整文件；**同一 `attribute` 内 `since` 单调不减**是 #32 的校验职责，不是格式职责。
6. **frontmatter 只放身份**：`subject`（必填）、可选 `title` / `aliases`。事实一律不写 frontmatter。

## 备选与取舍

| 方案 | 优点 | 代价 | 为什么没选 |
|---|---|---|---|
| frontmatter 块数组装映射 | 与其它域统一，一处解析 | 读取器不支持嵌套映射（实测读回成一个字符串） | 结构上不可用 |
| Markdown 表格 | 作者一眼能看懂，编辑器有对齐 | 中文与 `\|` 冲突频繁（`持有物 \| 备注`）；对齐行是噪声；改动一行会重排整表，diff 不可读；解析要额外处理对齐/转义 | 作者真正会手写的是列表，不是表格 |
| YAML 前后缀块（```yaml``` 代码块） | 可读、可多行 | 需要新的「块内解析」层，且代码块与正文混排时边界易错；同一文件里再嵌一套语法，读者要学两遍 | 收益只在「值很长」时出现，而账本的值通常是一个词 |
| 一条事实一个文件（`facts/<subject>-<attr>-<n>.md`） | 单文件单记录，解析最简单 | 与 §3.5 的文件粒度冲突；跨章校验要读 N 个文件；删改要算文件名 | 把「多条记录」的成本转移到文件系统上，得不偿失 |
| **正文列表项 + `\|` 分隔键值**（选中） | 与 `outlines/` 的情节点同一手感（都是正文列表项）；一行一条、diff 稳定、行锚天然；改动不动其它行 | 需要 `\|` 转义规则；值不能自然换行 | — |

## 后果

| 收益 | 代价与对策 |
|---|---|
| 一条事实 = 一行，findings 可精确到 `path#L<n>` | 换行即换锚：`locator` 只在同一次会话内可靠，跨次定位要重新解析（与其它域一致） |
| 增删一条事实只改一行 | `\|` 转义必须读写同源——`renderFactLine()` / `parseFactLine()` 成对出现，round-trip 用例守 |
| 未知键保留，未来加字段不改插件 | 未知键不参与校验，写错键名不会报错（与 frontmatter 同风险，接受） |
| 与 `outlines/` 的列表项手感一致 | 两处列表项语义不同（情节点 vs 事实），解析器不复用，只复用「行 → 结构」的思路 |

## 验证

- `tests/facts.test.js`：多事实解析；`\|` 转义 round-trip；未知键保留；缺省 `until` 视为未失效；`FACT_LINE_MALFORMED` 带 `path#L<n>`；同一 `subject` 两段 `since` 按章序聚合。
- round-trip 断言：解析 → 渲染 → 再解析，两次结果深相等（写回不改变作者原行以外的东西）。
